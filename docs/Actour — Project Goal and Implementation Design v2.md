# Actour v2：项目目标、架构与下一步工作路线

> 2026-09-22。本文是当前产品与实现路线的依据；[v1 草案](Actour%20%E2%80%94%20Project%20Goal%20and%20Implementation%20Design.md)仅供追溯早期想法。

## 1. 核心目标

Actour 是应用主动发布交互信息的基础设施。一个 Interaction Registration 描述一个稳定的 UI 目标：它是什么、当前能做什么、在屏幕哪里，以及现有 UI 事件如何触发。注册不以 Guide、Devtools 或 agent 中的某一个为目的；它们都是同一份信息的消费者。

产品能力沿着同一条链路生长：

```text
应用组件与原有事件处理函数
        ↓
Interaction Registration（稳定 ID、语义、操作、布局、状态）
        ├─ Guide：定位 target、绘制 overlay、等待真实操作
        ├─ Devtools：检查当前注册节点与状态
        └─ Agent：理解当前 UI、选择并执行允许的交互
                              ↑
                    Page Manifest / Guide Flow
                    目标、步骤关系与完成条件
```

应用继续持有业务状态、校验、导航和事件处理函数。Actour 不要求第二套 agent 专用业务流程。React Native 是唯一官方主平台；Actour 提供稳定 adapter 契约，但不承诺为所有 React renderer 维护官方实现。Taro 仅作为 adapter authoring demo，React Web 等平台由应用或社区按契约扩展。

## 2. 两种互补的信息

### 2.1 Node action：当前可执行什么

Interaction Registration 是基础输入。节点应能提供稳定 ID、简短 label / description、role、允许的操作、enabled / visible 状态，以及测得的 `x / y / width / height`。布局信息使 Guide 可以直接定位 target 并绘制 overlay；操作与语义使 agent 获得比遍历整棵组件树更精简的上下文。

组件适配器在注册时已经接触到 `onPress`、`onChangeText` 等现有处理入口。后续可以基于**显式注册的操作及参数描述**生成类似 function-call 的动作 schema，并由受控的 UI adapter 执行该操作，最终进入应用原有事件处理链。不能仅凭 lambda 推断业务参数、前置条件或安全级别，也不能因为注册了节点就默认允许 agent 自动调用。是否可自动执行须由页面策略或节点配置明确决定。

注册与注销跟随组件生命周期。节点状态变化通过 update 发布；消费者在需要决策时读取当前 snapshot。布局坐标需要随布局、滚动和窗口变化更新，执行前仍需确认目标处于有效状态。

### 2.2 Flow：为什么执行、何时推进

Page Manifest / Guide Flow 表达页面目标、步骤关系、相关节点、推进条件和完成条件。Guide 用它安排人的操作路径；agent 用它判断当前任务与哪些节点有关，以及何时继续、等待或停止。Flow 不复制业务逻辑，也不需要预先列出运行时才出现的每一个节点。

动态表单的典型循环：

```text
读取当前 flow 与已注册节点
  → 填写当前必填项
  → 应用更新 UI，新字段注册或现有字段更新
  → 重新读取节点和 flow 状态
  → 判断新字段是否属于当前目标、是否允许 agent 处理
  → 执行下一步或交还用户
```

因此 flow 提供任务边界，node 提供实时动作；二者相辅相成。Guide 的配置可以复用为 agent 的流程线索，但它不是不经校验就逐步执行的脚本。agent 的完成判断应以可观察的结果和 flow 完成条件为准。

## 3. 首版边界

首版以**显式 Interaction Registration** 建立可靠 target。基础交付聚焦 Guide：注册、定位、overlay、真实交互事件和流程推进。随后在同一信息层上增加 agent 可读的动作描述与受控执行。

Discovery-assisted 是旧项目无需逐个写 Interaction Registration 的最小改造路径，属于后续探索，**不属于首版交付承诺**。自动判断应观察哪些 button、switch、form 控件或 custom tag，以及它们的业务语义、参数和执行权限，不能只靠通用扫描可靠解决。它未来可以补充显式注册，但不能成为当前架构的前提。

## 4. 当前实现与差距

| 领域         | 当前仓库已有                                                         | 下一步需要补齐                                           |
| ------------ | -------------------------------------------------------------------- | -------------------------------------------------------- |
| Registry     | `register` / `unregister`、`update`、`snapshot`、结构与事件订阅      | 节点身份、状态与执行语义的契约；重复 ID 和过期注册的处理 |
| React Native | `InteractionPressable`、`InteractionTextInput`、布局测量、原事件转发 | 更多控件适配；滚动、遮挡、窗口变化下的位置与可操作性校验 |
| Guide        | target overlay、提示文案、按真实 press / input 事件推进              | 条件、跨页面流程、目标等待与自动滚动                     |
| Manifest     | v1 文档有概念示例                                                    | 可执行的页面 / flow 定义、节点关联与完成条件             |
| Agent        | 尚无执行桥接                                                         | 紧凑 snapshot、动作 schema、执行策略、结果验证与反馈     |
| Inspector    | 应用内展示当前节点                                                   | 展示语义、状态、布局与注册问题，辅助接入排查             |

当前代码中的 `visible` 初值、测量时机和事件模型满足示例引导，但还不足以支撑可靠的 agent 执行。文档中的目标能力不应被表述为已实现。

## 5. 下一步工作进程

Stage A 的基础实现已推进：注册句柄限定更新与注销的所有权，目标首次测量前保持不可见，引导运行时刷新当前目标的位置，并在目标缺失时等待而非绘制虚假的高亮。仍需在真实设备上验证滚动、遮挡和跨屏幕场景；这些结果会决定阶段 B 所需的目标状态契约。

### 阶段 A：稳固 Registration 与 Guide 基础

明确 `InteractionNode` 的字段、生命周期及稳定 ID 规则；让布局和 enabled / visible 状态可信；处理重复 ID、卸载、滚动和尺寸变化。Guide 在目标尚未出现时等待注册，在目标消失时明确处理，不把缺失 target 当作已完成。

**验收：**示例中目标可以随挂载、卸载和布局变化正确高亮；用户实际操作后推进；Inspector 能显示节点当前状态。应用原有 handler 只保留一份。

### 阶段 B：实现 Page Manifest 与 Flow

定义页面身份、目标、步骤关系、条件和完成条件。先支持显式配置的顺序与条件分支，再支持跨页面恢复和动态节点出现后的重新判断。Guide 基于同一 flow 运行；必要的业务判断通过应用提供的显式条件读取，不在 Actour 中复制业务校验。

**验收：**一个包含“填写必填项 → 出现新字段 → 继续填写 → 完成”的示例可由 Guide 正确推进；新字段无需在初始 snapshot 中存在。

### 阶段 C：开放受控的 agent 交互接口

从当前 registry 和 manifest 生成紧凑的可用节点与动作描述。对 press、输入等操作建立明确的参数 schema 和执行入口；执行前检查节点仍存在、可见、启用并获准自动执行，执行后重新观察 UI 与 flow 条件。对于无法推断参数或需要用户决策的节点，允许 agent 请求用户操作。

**验收：**agent 能在阶段 B 的动态表单中基于 flow 选择新出现的已注册节点，并通过应用原有 UI handler 完成任务；出现不允许自动执行的节点时停止并交还用户；结果有独立的完成条件验证。

### 阶段 D：评估 discovery-assisted 接入

在显式注册链路稳定后，对旧项目测试 accessibility、testID 和组件适配器能发现的目标，分别评估漏报、误报、语义质量与接入成本。根据验证结果决定支持哪些控件与 custom tag，不预设“全自动发现”范围或发布时间。

**验收方向：**用真实旧项目记录可发现率、需要人工补注的比例，以及错误暴露或错误执行的情况；形成明确的支持矩阵后再给出交付承诺。

## 6. 设计约束

1. 一次注册可供多个消费者使用，但每个消费者自行决定如何呈现或执行。
2. 应用原有 UI 事件与业务逻辑是唯一执行链；Actour 不维护并行的业务 handler。
3. Flow 提供目标与条件，注册节点提供实时能力；任一方不能单独代表完整的任务状态。
4. agent 只能看到当前任务所需的简短语义和有效动作；高风险或含糊操作需要显式策略与用户参与。
5. 性能目标是将注册成本分摊到组件生命周期，并在决策时读取小型 snapshot；实际收益要在接入真实应用后测量。

Actour 的核心价值不是某一种自动化算法，而是让现有应用用同一份交互信息，同时具备可引导的人类界面与可理解、可受控操作的机器界面。
